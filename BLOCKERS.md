# Blockers

Things that need input from the project owner. Each is stubbed so the build keeps moving; nothing here halts development.

## Awaiting credentials (the four allowed stop-and-ask items)

1. **Firebase project** — Android is real and wired in; iOS still needs `GoogleService-Info.plist`.
   - Status: `app/android/app/google-services.json` is a real config file for Firebase project `sokoni-71910` (package `tz.co.sokoni.sokoni`), and the Google Services Gradle plugin is applied for real — `com.google.gms.google-services` version `4.4.2` declared `apply false` in `android/settings.gradle.kts`'s `plugins {}` block, applied (no version) in `android/app/build.gradle.kts`. A debug build (`flutter build apk --debug`) confirms the plugin resolves and processes the config file with no errors. `app/lib/core/push/push_service.dart` is the real, complete client-side push registration flow (requests notification permission, gets an FCM token, POSTs it to `/devices`, re-registers on token refresh) triggered right after every successful sign-in (`AuthStateController` in `app/lib/core/providers.dart`) — this now actually runs on Android instead of failing at `Firebase.initializeApp()`.
   - Remaining: `app/ios/Runner/GoogleService-Info.plist` has not been provided, so iOS still fails soft at `Firebase.initializeApp()` exactly as before (caught, logged, rest of the app unaffected — chat's 5s polling doesn't depend on push). Server-side, `LogPushNotifier` still logs every push that would have been sent (new order, status change) in place of a real `kreait/laravel-firebase` sender — see `api/app/Services/Push/`.
2. ~~**Google Maps API key**~~ — **resolved by removal, not by waiting for billing** (tester feedback B3): `google_maps_flutter` is gone from the app entirely, replaced with `flutter_map` against OpenStreetMap's public tile server, which needs no API key and no billing account at all — the same no-key approach the website's own shop-location embeds already use. Both `DiscoveryMapView` and seller onboarding's step 2 now render a real, working map unconditionally; the `REPLACE_ME` placeholders and the `SokoniMapsConfig.isConfigured` gate that used to route around them have been removed from both native projects and from Dart. Nothing left blocked here.
3. **Google OAuth server client ID, Apple Sign-In Service ID**. (Facebook App ID is no longer on this list — see below.)
   - Stub: `google_sign_in` and `sign_in_with_apple` are fully integrated in `features/auth/presentation/social_sign_in_buttons.dart` — real native SDK flows, tokens verified server-side in `HttpSocialAuthVerifier` (never trusted client-side). Both buttons check `SokoniSocialAuthConfig` (`app/lib/core/config/social_auth_config.dart`, values read via `--dart-define`) and disable themselves with a tooltip while their ID is still the `REPLACE_ME` placeholder, since attempting the flow without a real ID fails inside the native SDK rather than failing cleanly. Server-side, `services.google.client_id` / `services.apple.client_id` in `api/.env` gate the same two flows — see `api/.env.example`.
   - **Facebook sign-in was removed entirely, not left pending.** This is no longer a "waiting on a credential" item — see DECISIONS.md for the full diagnosis. In short: `flutter_facebook_auth` 6.0.4's Android plugin constructs a `FacebookAuth()` (which initialises the native Facebook SDK) at plugin-registration time, unconditionally on every app launch, before any Dart code runs — and with no Facebook App ID ever configured, this was found hanging the entire app before Flutter's first frame on a real Android 16 device, confirmed via a diagnostic build variant that isolated the hang to native plugin registration. Removed the package from `pubspec.yaml`, the Facebook button and all related code from `social_sign_in_buttons.dart` and `SokoniSocialAuthConfig`, the Facebook branch from `HttpSocialAuthVerifier`/`SocialLoginRequest`/`config/services.php`, and the `FACEBOOK_APP_ID`/`FACEBOOK_APP_SECRET` vars from `.env.example`. Google, Apple, and phone OTP are unaffected. If Facebook sign-in is wanted again later, it needs re-evaluating against whichever Flutter Facebook-auth package is current at that time, not just re-adding this one.
4. **Production DB credentials for `sokoni.co.tz`** (cPanel MySQL).
   - Stub: `api/.env.example` documents every required var with placeholder values; local dev uses SQLite/local MySQL instead.

Leaving this on in production is a real information-disclosure risk, independent of anything else in this session.
