     1. **`GOOGLE_CLIENT_ID`** and **`GOOGLE_CLIENT_SECRET`** — from a Google Cloud Console project's **APIs & Services → Credentials → Create Credentials → OAuth client ID**, application type **Web application**. This can be the same OAuth client already used for the app's native sign-in, or a separate one — either works, since Socialite only ever needs a client id/secret pair, not a specific client type.
     2. Add an **Authorized redirect URI** on that same OAuth client, of the exact form `https://<your-domain>/auth/google/callback` — in production, `https://sokoni.co.tz/auth/google/callback` (or `https://beta.sokoni.co.tz/auth/google/callback` while still on the beta subdomain). Google rejects the callback outright if this doesn't match byte-for-byte (scheme, host, and path).

     - Also needs an **OAuth consent screen** configured on the same Google Cloud project (app name, support email, the logo if desired) — Google requires this before it will issue real tokens, separately from the OAuth client credentials themselves.
     - Once all three vars are set and the config cache is cleared (`php artisan config:clear`), the button appears automatically — no redeploy of code required, only the `.env` change.
   - **B9 (tester feedback, 2026-09-10): "Google sign-in inactive on both web and app" — re-audited end to end. Every code path (web Socialite redirect above, the app's native SDK flow, and server-side ID-token verification) is complete and correct; nothing here needed a code change. Confirmed by directly inspecting `app/android/app/google-services.json`: its `oauth_client` array is empty — no Android OAuth client has ever been issued for this app, because no signing certificate's SHA-1 fingerprint has ever been registered against it in the Firebase/Google Cloud console. That absence alone is enough to make the app's button fail at the native SDK level (the classic `ApiException: 10` / `DEVELOPER_ERROR`) even once `GOOGLE_SERVER_CLIENT_ID` is set — it is a separate, additional blocker from the web credential above, not the same one.**
     - **Exact steps, Android:** Firebase console → Project **sokoni-71910** → Project settings → your apps → the Android app (`tz.co.sokoni.sokoni`) → **Add fingerprint**, and paste in *both* of the following (extracted just now from the actual keystores already in this repo, so no separate `keytool` step is needed):
       - Debug (`~/.android/debug.keystore`, used by every local `flutter run`): `SHA1: 25:74:AF:F5:CB:FB:F9:D1:AF:E1:BD:9C:BC:CE:25:C7:B9:22:07:0D`
       - Release (`app/android/sokoni-release.jks`, alias `sokoni` — the one real release builds are signed with): `SHA1: 06:E8:90:E4:BF:F2:A8:59:38:6A:E2:A6:41:C1:93:9D:B6:F5:F7:30`
       - After adding both, re-download `google-services.json` from the same console page and replace `app/android/app/google-services.json` with it — this regenerates its `oauth_client` array with a real Android-type client for each fingerprint.
     - **The remaining piece is a *Web application* OAuth client** (Google Cloud Console → APIs & Services → Credentials → Create Credentials → OAuth client ID → **Web application** — the same kind of client item 3/C1 above already needs, and it can be the literal same client, not a second one). Its Client ID goes in **two different places that must hold the exact same value**:
       - `GOOGLE_SERVER_CLIENT_ID` — passed as a `--dart-define` at Android build time, consumed by `SokoniSocialAuthConfig.googleServerClientId` (`app/lib/core/config/social_auth_config.dart`), and given to `GoogleSignIn.instance.initialize(serverClientId: ...)` in `social_sign_in_buttons.dart`. This is what makes Google mint a server-verifiable ID token at all on Android — without it, no ID token is issued regardless of the SHA-1 fingerprint step above.
       - `GOOGLE_CLIENT_ID` — in `api/.env`, read by `config('services.google.client_id')`. `HttpSocialAuthVerifier::verifyGoogle()` checks the ID token's `aud` claim against exactly this value (`app/app/Services/SocialAuth/HttpSocialAuthVerifier.php`) — since Android's ID-token audience is always the `serverClientId` passed at initialize time, **these two values are required to be identical**, not independently configured. Setting them to two different client IDs (e.g. accidentally using an Android-type client ID for one of them, a common Google Sign-In mistake) fails silently as an "audience mismatch" rejection with no other symptom.
     - Nothing above requires touching the Dart or PHP code — it is entirely console configuration plus the two env values.

Removed the package from `pubspec.yaml`, the Facebook button and all related code from `social_sign_in_buttons.dart` and `SokoniSocialAuthConfig`, the Facebook branch from `HttpSocialAuthVerifier`/`SocialLoginRequest`/`config/services.php`, and the `FACEBOOK_APP_ID`/`FACEBOOK_APP_SECRET` vars from `.env.example`. Google, Apple, and phone OTP are unaffected. If Facebook sign-in is wanted again later, it needs re-evaluating against whichever Flutter Facebook-auth package is current at that time, not just re-adding this one.
