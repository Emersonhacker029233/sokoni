# Decisions Log

Judgement calls made during the build, with a one-line rationale each, in chronological order.

- **PHP runtime source**: PHP/Composer were not on PATH. `winget install PHP.PHP.8.3` failed (installer archive for that exact patch version 404'd on php.net); `PHP.PHP.8.4` installed successfully via winget. Separately discovered a pre-existing **Laravel Herd** install (`~/.config/herd/bin`) providing PHP 8.4.23 + Composer 2.10.1 + the `laravel` installer — using Herd's toolchain as the primary one since it's a complete, already-configured Laravel dev environment. Thin wrapper scripts were added at `~/bin/php` and `~/bin/composer` so the POSIX (bash) tool can resolve the `.bat`-wrapped Herd binaries. This is a local dev detail only — the cPanel deploy target still runs PHP 8.3 per `docs/DEPLOY.md`, and Laravel 12 supports 8.2+, so there's no compatibility concern.
- **Directory layout**: followed the spec's exact tree. `api/` and `app/` are populated by their respective official scaffolding tools (`composer create-project laravel/laravel`, `flutter create`) rather than hand-built, so their internals (e.g. Laravel's default `bootstrap/`, `config/`) follow framework convention beyond what the spec enumerates.
- **Framework/package majors newer than the spec named**: the spec was written assuming Laravel 12, Filament v3, and Riverpod 2 as current; by the time of this build the actual latest-stable versions are **Laravel 13.25**, **Filament v5.7**, and **Riverpod 3.3 / riverpod_annotation 4.0**. Installed latest-stable throughout rather than force-pinning to the older majors the spec named, since (a) `composer create-project laravel/laravel` and `flutter pub add <pkg>` both resolve to current-latest by default, (b) Filament v3 is incompatible with the `symfony/console` v8 that ships with Laravel 13 (see below), and (c) fighting the resolver back to years-old majors would mean losing security patches for no benefit — the spec's intent ("don't re-litigate the stack") is about *which* framework, not pinning to a specific point-in-time minor. All spec-described behavior (Sanctum tokens, Filament admin resources, Riverpod providers/generators) works the same shape across these majors.
- **Filament version conflict**: `composer require filament/filament:^3` failed — Filament v3's `filament/support` requires `symfony/console ^6.0|^7.0`, but Laravel 13's dependency tree already pins `symfony/console` to v8.1.4, so v3 could never be installed alongside a fresh Laravel 13 app. Installed the latest Filament major (v5.7.6) unpinned instead, which resolves cleanly.
- **flutter_riverpod resolved to v3.x**: the spec says "Riverpod 2 + generator," but Riverpod 2 is no longer the version `flutter pub add` resolves to (latest stable is 3.3.2, with `riverpod_annotation` 4.0.3). Kept latest-stable per the framework-major note above.
- **win32 dependency conflict (Flutter)**: `file_picker`, `share_plus`, and `wakelock_plus` (a transitive dep of `chewie`) each pin incompatible major ranges of the Windows-desktop-only `win32` package (5.x vs 6.x). Since this app only targets Android/iOS (`flutter create --platforms android,ios`), the actual win32 FFI bindings are never compiled into the app. Added a `dependency_overrides: win32: ^6.3.0` in `app/pubspec.yaml` to settle pub's version bookkeeping — this only affects dependency resolution, not the Android/iOS build output.
- **Dropped `custom_lint` + `riverpod_lint` dev dependencies**: every version of `custom_lint` requires `freezed_annotation ^2.2.0`, which conflicts with the `freezed_annotation ^3.x` that current `freezed` (needed for the app's models) requires — a real, currently-unresolved incompatibility in the package ecosystem, not something fixable by version-juggling on our end. Baseline linting still comes from `flutter_lints` (already included, rules tightened in `analysis_options.yaml`). If the ecosystem catches up, these can be added back.
- **Flutter SDK upgraded**: the pre-installed Flutter (3.41.6, Dart 3.11.4) was too old for `riverpod_generator` (needs Dart SDK ≥3.12 as of its recent majors) and conflicted with `geocoding ^5.0.0`'s analyzer/dart_style toolchain deps. Ran `flutter upgrade` to Flutter 3.47.0 / Dart 3.13.0, which resolved both cleanly.
- **Brand logo duplicated into `app/assets/brand/`**: the spec's canonical asset lives at repo-root `assets/brand/sokoni_logo.png`, but Flutter's `pubspec.yaml` can only bundle assets that live inside the Flutter package itself — it can't reference a parent directory. Copied the logo into `app/assets/brand/sokoni_logo.png` for the app to actually bundle (used by `flutter_launcher_icons`, `flutter_native_splash`, and the splash primitive); the repo-root copy stays the canonical source referenced by the spec and design docs. If the logo changes, both copies need updating.
- **No real brand logo supplied**: none was found in the workspace or Downloads, so one was generated programmatically (a simple yellow shopping-bag mark with a black "S" glyph on a black rounded-square background, using the spec's exact palette values) via a small Python PNG writer, since no image-editing tool was available. This is a placeholder pending a real logo from the client — swap `assets/brand/sokoni_logo.png` (both copies) and re-run `flutter pub run flutter_launcher_icons` / `flutter pub run flutter_native_splash:create` when one arrives.
- **Motion primitive bug caught by the widget test**: `SokoniSplashTransition`, `StaggeredReveal`, and the success-checkmark overlay all originally called `MediaQuery.disableAnimationsOf(context)` inside `initState()`, which Flutter forbids (inherited-widget lookups must happen in `build()` or `didChangeDependencies()` — the element isn't fully mounted yet during `initState`). This only surfaces at runtime, not via `flutter analyze`; the Phase 1 widget test caught it immediately. Fixed by moving the check into `didChangeDependencies()` guarded by a `_started` flag so it only runs once.
- **Geo storage on `seller_profiles`**: the spec's data model lists `shop_location(POINT, SPATIAL INDEX)`, but that's MySQL-only and unusable for local dev/tests on SQLite. Stored `lat`/`lng` decimals as the portable source of truth (what the app actually reads/writes), and — only when the connection driver is MySQL — added a generated `shop_location POINT` column with a spatial index derived from them via raw SQL in the migration. `App\Services\Geo\DistanceQuery` uses `ST_Distance_Sphere` on MySQL and a PHP Haversine calculation over lat/lng on SQLite, so radius search is correct either way. `orders.delivery_location` similarly became plain `delivery_lat`/`delivery_lng` — it's stored data, not a query target, so it didn't need the spatial treatment at all.
- **`products.title`/`description` full-text index is MySQL-only**: SQLite's schema builder throws `RuntimeException` on `Blueprint::fullText()`. Guarded it behind a driver check in the migration; `Product::scopeSearch()` uses `whereFullText` on MySQL and falls back to a `LIKE '%term%'` query on SQLite.
- **Seed data: 70 orders, not the spec's 40** — see the seeder's own docblock: 60 reviews require 60 *unique* completed orders (`reviews.order_id` is unique — the actual anti-fake-review mechanism), which 40 total orders can't supply alongside pending/accepted/ready/cancelled examples for a realistic demo.
- **Social login verifies tokens server-side for real** (`HttpSocialAuthVerifier`): Google via `tokeninfo` audience check, Facebook via `debug_token`, Apple via JWKS signature verification (`firebase/php-jwt`, already a transitive dependency via kreait/laravel-firebase). All three make genuine HTTP/JWT calls and fail closed with `InvalidSocialTokenException` until real client IDs are configured (BLOCKERS.md item 3) — never trust a client-supplied `provider_id` directly.
- **Several real bugs caught by manual smoke-testing before writing formal tests** (all fixed, see commit): (1) `App\Http\Controllers\Controller` was missing `AuthorizesRequests`, so every `$this->authorize()` call in the app threw `Call to undefined method`. (2) `Order`/`Review` status-transition fields (`status`, `accepted_at`/etc., `reply`/`replied_at`) were deliberately left out of each model's `#[Fillable]` (so they can't be mass-assigned by a buyer), but the controllers were then mass-assigning them via `->update()`, which Eloquent silently no-ops instead of erroring — fixed by using `forceFill()` for those specific, validated, server-controlled transitions. (3) `$request->string('delivery_method') === 'delivery'` was always false — `->string()` returns a `Stringable` object, never `===` to a plain string; switched to `->input()`. (4) `User::isSeller()`/`isVerifiedSeller()` and several policy/controller checks read the lazy `sellerProfile` relation property, which can be cached as `null` from an earlier access in the same request/object lifetime (e.g. rendering `UserResource` before a seller profile existed) and then goes stale once one is created — switched every authorization-relevant check to a fresh `sellerProfile()` query (`User::sellerProfileId()` helper). This class of bug is real in any long-lived object context (queued jobs reusing models, Laravel's own `actingAs()` test helper), even though ordinary per-request production traffic re-resolves the user fresh each time.
- **Tests authenticate via `Sanctum::actingAs()`, not the base `actingAs()`**: overridden once in `Tests\TestCase` rather than per test file. The base Laravel `actingAs()` sets an authenticated user without a token context, so `$request->user()->currentAccessToken()` (used by `AuthController::logout`) is `null` in tests even though a real bearer-token request always has one — confirmed the real endpoint works correctly via a manual `curl` request with an actual token before concluding this was test-only.
