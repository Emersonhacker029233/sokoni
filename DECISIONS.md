# Decisions Log

Judgement calls made during the build, with a one-line rationale each, in chronological order.

- **PHP runtime source**: PHP/Composer were not on PATH. `winget install PHP.PHP.8.3` failed (installer archive for that exact patch version 404'd on php.net); `PHP.PHP.8.4` installed successfully via winget. Separately discovered a pre-existing **Laravel Herd** install (`~/.config/herd/bin`) providing PHP 8.4.23 + Composer 2.10.1 + the `laravel` installer — using Herd's toolchain as the primary one since it's a complete, already-configured Laravel dev environment. Thin wrapper scripts were added at `~/bin/php` and `~/bin/composer` so the POSIX (bash) tool can resolve the `.bat`-wrapped Herd binaries. This is a local dev detail only — the cPanel deploy target still runs PHP 8.3 per `docs/DEPLOY.md`, and Laravel 12 supports 8.2+, so there's no compatibility concern.
- **Directory layout**: followed the spec's exact tree. `api/` and `app/` are populated by their respective official scaffolding tools (`composer create-project laravel/laravel`, `flutter create`) rather than hand-built, so their internals (e.g. Laravel's default `bootstrap/`, `config/`) follow framework convention beyond what the spec enumerates.
- **Framework/package majors newer than the spec named**: the spec was written assuming Laravel 12, Filament v3, and Riverpod 2 as current; by the time of this build the actual latest-stable versions are **Laravel 13.25**, **Filament v5.7**, and **Riverpod 3.3 / riverpod_annotation 4.0**. Installed latest-stable throughout rather than force-pinning to the older majors the spec named, since (a) `composer create-project laravel/laravel` and `flutter pub add <pkg>` both resolve to current-latest by default, (b) Filament v3 is incompatible with the `symfony/console` v8 that ships with Laravel 13 (see below), and (c) fighting the resolver back to years-old majors would mean losing security patches for no benefit — the spec's intent ("don't re-litigate the stack") is about *which* framework, not pinning to a specific point-in-time minor. All spec-described behavior (Sanctum tokens, Filament admin resources, Riverpod providers/generators) works the same shape across these majors.
- **Filament version conflict**: `composer require filament/filament:^3` failed — Filament v3's `filament/support` requires `symfony/console ^6.0|^7.0`, but Laravel 13's dependency tree already pins `symfony/console` to v8.1.4, so v3 could never be installed alongside a fresh Laravel 13 app. Installed the latest Filament major (v5.7.6) unpinned instead, which resolves cleanly.
- **flutter_riverpod resolved to v3.x**: the spec says "Riverpod 2 + generator," but Riverpod 2 is no longer the version `flutter pub add` resolves to (latest stable is 3.3.2, with `riverpod_annotation` 4.0.3). Kept latest-stable per the framework-major note above.
- **win32 dependency conflict (Flutter)**: `file_picker`, `share_plus`, and `wakelock_plus` (a transitive dep of `chewie`) each pin incompatible major ranges of the Windows-desktop-only `win32` package (5.x vs 6.x). Since this app only targets Android/iOS (`flutter create --platforms android,ios`), the actual win32 FFI bindings are never compiled into the app. Added a `dependency_overrides: win32: ^6.3.0` in `app/pubspec.yaml` to settle pub's version bookkeeping — this only affects dependency resolution, not the Android/iOS build output.
- **Dropped `custom_lint` + `riverpod_lint` dev dependencies**: every version of `custom_lint` requires `freezed_annotation ^2.2.0`, which conflicts with the `freezed_annotation ^3.x` that current `freezed` (needed for the app's models) requires — a real, currently-unresolved incompatibility in the package ecosystem, not something fixable by version-juggling on our end. Baseline linting still comes from `flutter_lints` (already included, rules tightened in `analysis_options.yaml`). If the ecosystem catches up, these can be added back.
- **Flutter SDK upgraded**: the pre-installed Flutter (3.41.6, Dart 3.11.4) was too old for `riverpod_generator` (needs Dart SDK ≥3.12 as of its recent majors) and conflicted with `geocoding ^5.0.0`'s analyzer/dart_style toolchain deps. Ran `flutter upgrade` to Flutter 3.47.0 / Dart 3.13.0, which resolved both cleanly.
- **Brand logo duplicated into `app/assets/brand/`**: the spec's canonical asset lives at repo-root `assets/brand/sokoni_logo.png`, but Flutter's `pubspec.yaml` can only bundle assets that live inside the Flutter package itself — it can't reference a parent directory. Copied the logo into `app/assets/brand/sokoni_logo.png` for the app to actually bundle (used by `flutter_launcher_icons`, `flutter_native_splash`, and the splash primitive); the repo-root copy stays the canonical source referenced by the spec and design docs. If the logo changes, both copies need updating.
- **No real brand logo supplied**: none was found in the workspace or Downloads, so one was generated programmatically (a simple yellow shopping-bag mark with a black "S" glyph on a black rounded-square background, using the spec's exact palette values) via a small Python PNG writer, since no image-editing tool was available. This is a placeholder pending a real logo from the client — swap `assets/brand/sokoni_logo.png` (both copies) and re-run `flutter pub run flutter_launcher_icons` / `flutter pub run flutter_native_splash:create` when one arrives.
- **Motion primitive bug caught by the widget test**: `SokoniSplashTransition`, `StaggeredReveal`, and the success-checkmark overlay all originally called `MediaQuery.disableAnimationsOf(context)` inside `initState()`, which Flutter forbids (inherited-widget lookups must happen in `build()` or `didChangeDependencies()` — the element isn't fully mounted yet during `initState`). This only surfaces at runtime, not via `flutter analyze`; the Phase 1 widget test caught it immediately. Fixed by moving the check into `didChangeDependencies()` guarded by a `_started` flag so it only runs once.
- **Geo storage on `seller_profiles`**: the spec's data model lists `shop_location(POINT, SPATIAL INDEX)`, but that's MySQL-only and unusable for local dev/tests on SQLite. Stored `lat`/`lng` decimals as the portable source of truth (what the app actually reads/writes), and — only when the connection driver is MySQL — added a generated `shop_location POINT` column with a spatial index derived from them via raw SQL in the migration. `App\Services\Geo\DistanceQuery` uses `ST_Distance_Sphere` on MySQL and a PHP Haversine calculation over lat/lng on SQLite, so radius search is correct either way. `orders.delivery_location` similarly became plain `delivery_lat`/`delivery_lng` — it's stored data, not a query target, so it didn't need the spatial treatment at all.
- **`products.title`/`description` full-text index is MySQL-only**: SQLite's schema builder throws `RuntimeException` on `Blueprint::fullText()`. Guarded it behind a driver check in the migration; `Product::scopeSearch()` uses `whereFullText` on MySQL and falls back to a `LIKE '%term%'` query on SQLite.
- **Seed data: 70 orders, not the spec's 40** — see the seeder's own docblock: 60 reviews require 60 *unique* completed orders (`reviews.order_id` is unique — the actual anti-fake-review mechanism), which 40 total orders can't supply alongside pending/accepted/ready/cancelled examples for a realistic demo.
- **Social login verifies tokens server-side for real** (`HttpSocialAuthVerifier`): Google via `tokeninfo` audience check, Facebook via `debug_token`, Apple via JWKS signature verification (`firebase/php-jwt`, already a transitive dependency via kreait/laravel-firebase). All three make genuine HTTP/JWT calls and fail closed with `InvalidSocialTokenException` until real client IDs are configured (BLOCKERS.md item 3) — never trust a client-supplied `provider_id` directly.
- **Several real bugs caught by manual smoke-testing before writing formal tests** (all fixed, see commit): (1) `App\Http\Controllers\Controller` was missing `AuthorizesRequests`, so every `$this->authorize()` call in the app threw `Call to undefined method`. (2) `Order`/`Review` status-transition fields (`status`, `accepted_at`/etc., `reply`/`replied_at`) were deliberately left out of each model's `#[Fillable]` (so they can't be mass-assigned by a buyer), but the controllers were then mass-assigning them via `->update()`, which Eloquent silently no-ops instead of erroring — fixed by using `forceFill()` for those specific, validated, server-controlled transitions. (3) `$request->string('delivery_method') === 'delivery'` was always false — `->string()` returns a `Stringable` object, never `===` to a plain string; switched to `->input()`. (4) `User::isSeller()`/`isVerifiedSeller()` and several policy/controller checks read the lazy `sellerProfile` relation property, which can be cached as `null` from an earlier access in the same request/object lifetime (e.g. rendering `UserResource` before a seller profile existed) and then goes stale once one is created — switched every authorization-relevant check to a fresh `sellerProfile()` query (`User::sellerProfileId()` helper). This class of bug is real in any long-lived object context (queued jobs reusing models, Laravel's own `actingAs()` test helper), even though ordinary per-request production traffic re-resolves the user fresh each time.
- **Tests authenticate via `Sanctum::actingAs()`, not the base `actingAs()`**: overridden once in `Tests\TestCase` rather than per test file. The base Laravel `actingAs()` sets an authenticated user without a token context, so `$request->user()->currentAccessToken()` (used by `AuthController::logout`) is `null` in tests even though a real bearer-token request always has one — confirmed the real endpoint works correctly via a manual `curl` request with an actual token before concluding this was test-only.
- **Riverpod providers hand-written, not `@riverpod`-generated, for core infra** (`core/providers.dart`: Dio, drift, secure storage, auth state, connectivity): these are plain singleton services with no need for the generator's family/auto-dispose ergonomics, and skipping codegen here avoids a build_runner round-trip for infrastructure that rarely changes. Reserving `riverpod_generator` for feature-level data providers (Phase 4+) where its caching actually earns its keep.
- **`data/api` uses retrofit as the spec's file tree specifies**, but two `AuthApi` methods (`me()`, `acceptTerms()`) are typed `Future<dynamic>` rather than `Future<Map<String, dynamic>>`: retrofit_generator mis-generates a `dynamic.fromJson(...)` call (which doesn't exist) when the declared return type is literally `Map<String, dynamic>`. `dynamic` sidesteps the codegen bug; the repository still safely indexes `json['data']` either way.
- **Auth UI pulled slightly ahead of Phase 6**: rather than leave the Profile/Orders/Sell tabs' "Sign in" buttons non-functional until the seller-onboarding phase, built a minimal but fully working phone-OTP sign-in bottom sheet now (`features/auth/presentation/phone_sign_in_sheet.dart`) against the Phase 2 API. Google/Facebook/Apple buttons and the 4-step seller wizard remain Phase 6 — a dead button would have been worse than a real slice of auth built early.
- **go_router's `StatefulShellRoute.indexedStack()` factory doesn't expose `navigatorContainerBuilder`** (it's hardcoded to a plain, non-animated `IndexedStack`), so the fade-through tab-switch motion primitive needs the base `StatefulShellRoute(...)` constructor instead, with a custom `navigatorContainerBuilder` (`FadeThroughIndexedStack` in `app_shell.dart`) that fades the container on branch change while `IndexedStack` still keeps every branch's Navigator/scroll state alive underneath.
- **Nav bar item index ≠ shell branch index**: the 5 router branches are `[home, search, sell, orders, profile]`, but `AnimatedNavBar` only renders 4 tab icons (Sell is the centre FAB instead), so item index 2 in the nav bar is "orders" while branch index 2 is "sell". `AppShell` maps between them explicitly (`_navItemBranchIndexes`) rather than assuming they line up — passing the raw tab index straight to `goBranch()` would have silently opened the wrong tab from "Orders" onward.
- **`sqlite3_flutter_libs` is now a no-op stub package** (kept only so other packages can still depend on `0.6.0` after the underlying `sqlite3` package went to v3.x, which bundles its own native-library loading) — its `applyWorkaroundToOpenSqlite3OnOldAndroidVersions()` function no longer exists. Removed the call; drift's `NativeDatabase.createInBackground` works without it on the current sqlite3.
- **`SellerSummaryResource` gained `lat`/`lng`**: the discovery map view (CLAUDE.md feature 1) needs real seller coordinates to place pins. The first pass jittered fake pin positions around the search centre to work around `ProductResource` only exposing `distance_km`; that produced pins at *wrong* locations, which is worse than deferring the feature — a genuinely misleading map is not "a real implementation with a mocked external call," the bar the spec sets for what's allowed to be incomplete. Fixed at the source instead: `seller_profiles.lat`/`lng` were already stored, just not serialized on the compact seller embed, so exposing them (nullable, only when set) was the correct fix rather than a client-side workaround.
- **Marker clustering deferred**: `google_maps_flutter` has no built-in pin clustering; the discovery map places one real, correctly-positioned marker per seller, but doesn't visually merge nearby pins at low zoom. A dedicated clustering package is a reasonable follow-up, not urgent enough to pull into this build alongside everything else in Phase 4.
- **`ProductCard` widget test wraps it in a fixed-aspect-ratio `SizedBox`**, not a bare `Scaffold`: the card's square cover image plus its text block only fit within the `childAspectRatio: 0.62` grid cell the discovery/search grids actually give it (see `home_screen.dart`/`search_screen.dart`) — an unconstrained parent height correctly overflows, since that's not how the widget is ever really used. The first version of the test used a bare `Scaffold` and caught this immediately.
- **Widget tests override `dioProvider` with a fail-fast `HttpClientAdapter`** rather than leaving real network calls unmocked: any screen that fires a provider-driven API call on build (the home feed does, immediately) leaves a pending `Timer`/microtask when `flutter test` tears down before a real request would resolve or time out, which `flutter test` treats as a hard failure ("A Timer is still pending"). Failing the request synchronously exercises `ProductRepository`'s existing offline-cache fallback path instead, which is both faster and closer to a real "offline" scenario than an unmocked hang.
- **`SellerSummaryResource` gained `whatsapp`** (toggleable via the existing `show_whatsapp` flag), for the same reason it gained `lat`/`lng` in Phase 4: the WhatsApp deep-link button on the product detail page needs the seller's real number. The first draft of that button used the seller's database *id* as the phone number — caught immediately since it's an obviously-wrong value, but it's the same underlying pattern as the map-pin bug: a compact embed missing a field the UI actually needs, worth fixing at the API rather than routing around client-side.
- **Added `Product::scopeForSeller()` + a `seller_id` filter on `GET /products`**: the shop profile's Products/Gallery tabs need one seller's products, and the discovery endpoint had no way to ask for that. Small, backward-compatible addition (defaults to no filtering) rather than a separate endpoint, consistent with how `category_id`/`q`/`sort` already work.
- **Every `Navigator.of(context).pushNamed(...)` call written during this phase was a bug**: this app uses go_router exclusively (`MaterialApp.router`) with no named-route table configured via `MaterialApp.routes`, so `pushNamed` would have failed at runtime for every "tap a product/shop/message" action — analyze doesn't catch this since `pushNamed` is a real, valid `Navigator` method, just one this app never wires up. Replaced with `context.push(SokoniRoutes.xxx(...))` throughout and added the missing route definitions (`/products/:id`, `/shop/:handle`, `/conversations/:id`, `/favorites`) to `app_router.dart`. Worth flagging in case the same mistake recurs in Phase 6+.
- **`geocoding` v5's public API is instance-based, not top-level functions**: earlier Sokoni code assumed a free `placemarkFromCoordinates(...)` function (the pre-v5 API); v5 requires constructing a `Geocoding()` instance and calling the method on it. Fixed in the onboarding location step (`step2_location.dart`) rather than pinning an older `geocoding` version, since the instance API is otherwise equivalent.
- **`file_picker`'s Windows implementation (11.0.3, the current latest) is written against `win32` 5.x's API and fails to compile under `win32` 6.x** (`HRESULT` became a distinct extension type, `convertToIID` was renamed, `IShellItem.getDisplayName`'s signature changed) — a real upstream incompatibility, not just a semver-range mismatch. The `win32: ^6.3.0` override added earlier (to reconcile `file_picker`/`share_plus`/`wakelock_plus`'s differing win32 ranges) satisfied pub's version solver but silently broke `file_picker`'s actual Windows source, which only surfaces when something forces a full compile of the host-platform plugin registrant — `flutter analyze` doesn't do this, but `flutter test` does (it always builds for the Windows host on this dev machine, even though the app itself only targets Android/iOS and has no `windows/` platform folder). Fixed by lowering the override to `win32: ^5.9.0`; pub then resolves compatible (older) `share_plus`/`wakelock_plus` versions automatically, and all three packages' actual Windows source compiles cleanly again. Purely a local dev-loop fix — irrelevant to the shipped Android/iOS build either way — but needed for `flutter test` to run at all on this machine.
- **`FilePicker`'s static entry point in v11 is `FilePicker.pickFiles(...)` directly**, not `FilePicker.platform.pickFiles(...)` (the pre-federated-plugin-refactor API) — used directly in the licence-upload step (`step4_licence.dart`).
- **`product_media` gained a `card_path` column**: CLAUDE.md's media feature explicitly calls for three generated sizes ("thumb 300, card 800, full 1600"), but the original migration only had two URL columns (`path`, `thumb_path`). Rather than silently dropping the middle size to fit the existing schema, added `card_path` via a new migration — `path` is the 1600px full/detail-carousel image, `card_path` the 800px general-purpose size, `thumb_path` the 300px grid/list thumbnail. Video rows only populate `thumb_path` (a poster frame) since there's no "full-size video" concept.
- **Video thumbnails are supplied by the client, not generated server-side**: `ProductMediaStoreRequest` requires a `thumbnail` image alongside any video upload. Generating a poster frame from video server-side needs an `ffmpeg` binary, which isn't guaranteed (or installable) on Namecheap shared hosting — the deploy target this app is built for. The client already compresses video with `video_compress` before upload (CLAUDE.md feature 7), and that package can extract a frame directly, so producing the poster client-side avoids a server dependency the production host can't reliably provide.
- **`product_media.path`/`thumb_path`/`card_path` store full public URLs, not disk-relative paths**: matches the existing seeded convention (`ProductMediaFactory` already stores absolute `picsum.photos` URLs) and what the Flutter client already assumes (`ProductCard`/`ProductMediaCarousel` pass these fields straight to `CachedNetworkImage` with no base-URL prefixing). `ProductMediaController` stores via `Storage::disk('public')->url(...)` accordingly.
- **Added `GET /shop/products`** (mirrors the existing `GET /shop/orders` pattern): the public `GET /products` index always applies `Product::visible()`, which a seller's own My Shop dashboard can't use — a pending or newly-added-but-inactive product needs to show up on the seller's own dashboard even though it's correctly hidden from public discovery (CLAUDE.md feature 4).
- **`OrderResource` gained `conversation_id`**: CLAUDE.md feature 8 says the order thread "opens automatically in chat" on placement — the client needs the new conversation's id right out of the checkout response to navigate straight there, rather than making a second round-trip to list conversations and match by `order_id`.
- **`ProductResource` gained `is_active`/`is_hidden`**: neither was exposed to clients before Phase 7, which was fine while nothing needed them, but the My Shop dashboard is the seller's own view of their products and has to be able to show "this one's inactive" / explain why something isn't showing in the public feed (e.g. auto-hidden after three upheld reports, CLAUDE.md feature 11) — information the owner needs that a stranger browsing the public feed doesn't.
- **Cart is a plain in-memory Riverpod `Notifier`, not persisted to drift**: CLAUDE.md's cart is explicitly single-seller and checkout-in-one-sitting (no saved-for-later concept anywhere in the spec), so there's no real scenario where surviving an app restart matters enough to justify a persistence layer for it — losing an in-progress cart on a kill is an acceptable, standard mobile-commerce trade-off here.
- **Riverpod gotcha, caught before shipping**: `ref.watch(cartProvider.notifier).subtotal` does *not* rebuild the widget when cart contents change — watching `.notifier` subscribes to the controller instance (which never changes for a `Notifier`), not its state. Any derived value read off a controller needs the *state* provider (`ref.watch(cartProvider)`) watched directly and computed from that. Fixed in both `cart_screen.dart` and `checkout_screen.dart` before it shipped as a "totals never update" bug — worth remembering for any future derived-value read off a Notifier.
- **Video thumbnails, again, client-side**: the product-form's video picker uses `video_compress`'s `getFileThumbnail()` to produce the poster frame it uploads alongside the compressed clip — same reasoning as the server-side decision above (no `ffmpeg` on the shared-hosting deploy target), just the client half of it.
- **"Am I the buyer or the seller on this order" is derived by comparing `currentUser.id == order.buyer.id`**, not by comparing seller-profile ids: `UserResource` doesn't expose a seller-profile id (no client-side use for it existed before Phase 7), and the backend's `OrderPolicy::view` already guarantees only the buyer or the owning seller can ever fetch an order in the first place — so "not the buyer" reliably means "the seller" for anyone who can see the order at all, without needing a new field.
- **Firebase push registration is fully implemented client-side but fails soft with no project configured yet** (BLOCKERS.md item 1): `PushService.registerDevice()` calls the real `firebase_core`/`firebase_messaging` APIs and POSTs a real token to `/devices`, triggered on every successful sign-in. With no `google-services.json`/`GoogleService-Info.plist`, `Firebase.initializeApp()` throws on the very first call (there's no native default to fall back to) — caught and logged there, so the rest of the app is unaffected; chat still works via polling regardless of push. Found and corrected a stale BLOCKERS.md claim from an earlier session that this was already wired behind a `firebase_options.dart` — it wasn't; nothing under `core/push/` existed until this phase.
- **A typing indicator over 5s polling is implemented as a real per-party "typing until" timestamp**, not simulated client-side: `conversations` gained `buyer_typing_until`/`seller_typing_until` columns, refreshed via a small `PATCH /conversations/{id}/typing` the client calls (debounced to once per 3s) while the user types, and read back on the same poll cycle that already fetches messages every 5s. CLAUDE.md explicitly lists a typing indicator as a chat feature despite the no-WebSocket architecture, and "no placeholder code" rules out faking it locally with no signal from the other device — this is the honest real-time-with-latency equivalent, accurate to within the existing 5s poll cadence rather than instant.
- **Chat image attachments and product-media are stored the same way**: `MessageController::store` now runs the uploaded attachment through `Storage::disk('public')->url()` before saving, matching `ProductMediaController`'s convention — previously it stored the bare disk-relative path (`chat/xxx.jpg`), which the client can't load directly since it has no notion of the storage disk's base URL. Caught while wiring the Phase 8 chat thread UI, which would otherwise have rendered broken images for every attachment.
- **`UserResource` gained `seller_handle`**: the shop review tab needs to know whether the currently signed-in user *is* the shop's owner (to show/hide the "Reply" button), and the only clean signal for that already used elsewhere (`order.buyer.id` comparison for orders) doesn't apply here — a review has no buyer/seller-relative viewer to compare against directly. Comparing the viewer's own `seller_handle` against the shop `handle` being viewed is a direct, honest check reusing a field-per-need pattern already established for `seller_status` on the same resource.
- **Riverpod family `AsyncNotifier` pattern**: `ChatThreadController` (one polling timer per open conversation) is a hand-written, non-codegen family notifier — `AsyncNotifierProvider.autoDispose.family<ChatThreadController, ThreadState, int>(ChatThreadController.new)`, where the family argument is threaded through the notifier's own constructor parameter (`ChatThreadController(this.conversationId)`), not through `build(arg)` — `AsyncNotifier.build()` stays zero-argument even for family notifiers in this (non-generator) API. First hand-written family notifier in the codebase; worth remembering the constructor-carries-the-arg shape if another one comes up.
- **Filament panel installed and built out in Phase 9**, not earlier: `composer.json` had `filament/filament` since Phase 0 and `User implements FilamentUser` (with `canAccessPanel()` gating on `is_admin`) was already written back in Phase 2 anticipating this, but `php artisan filament:install --panels` itself — the step that actually creates `AdminPanelProvider` and registers it in `bootstrap/providers.php` — had never been run. No admin UI existed until this phase despite the scaffolding being in place.
- **Generated Filament resources dropped their create/edit pages where there's no legitimate reason for an admin to hand-create that record**: `SellerProfileResource` and `ReportResource` are pure review-and-decide surfaces (sellers create profiles through the app's onboarding wizard; reports are only ever created by users through the app's report flow) — keeping Filament's auto-generated Create/Edit pages around would have let an admin "edit" fields like `status`/`verified_at` that aren't even mass-assignable (`SellerProfile`/`Report` deliberately exclude them from `#[Fillable]` for the same reason `Order`'s status fields are excluded), producing a form that silently no-ops on save. `UserResource` and `CategoryResource` kept theirs, since creating a staff/admin account or a new category are real, legitimate admin actions.
- **Seller verify/reject and the moderation queue's uphold/dismiss/hide/warn/suspend/ban all use `forceFill()` inside Filament `Action` closures**, not the framework's default record-update behavior: same reasoning as everywhere else in the codebase that a status transition is deliberately excluded from a model's `#[Fillable]` — these are validated, server-controlled transitions, not free-form field edits, so a plain `update()` call would silently drop them.
- **"Suspend" needed its own schema fields, not just reuse of `banned_at`**: CLAUDE.md feature 11 lists hide/warn/suspend/ban as four distinct admin actions, but the spec's own data model only persists `banned_at` — no way to distinguish a temporary suspension from a permanent ban, and no field to persist *why* (only an ephemeral push-notification body would carry the reason otherwise). Added `banned_until` (null = permanent ban, set = suspension expiring at that time) and `ban_reason` (persisted, not just pushed) — the same "action + persisted reason" pattern already used for `SellerProfile.rejection_reason` and `Order.cancelled_reason`. `User::isBanned()` now treats an expired `banned_until` as no-longer-banned automatically.
- **Suspending/banning a user also revokes their existing Sanctum tokens** (`$user->tokens()->delete()`), not just their ability to get a *new* one: `AuthController::issueToken()` already blocked banned users from signing in, but a user banned mid-session would have kept using their existing bearer token indefinitely otherwise — the ban wouldn't take effect until their token happened to expire.
- **`Report::offendingUser()` added to resolve "the user behind this content"** for warn/suspend/ban actions: each of the three reportable types (`Product`, `SellerProfile`, `Message`) reaches its owning user through a different relationship chain (`product.seller.user`, `sellerProfile.user`, `message.sender`), and the moderation queue needs one uniform way to act on "this account," regardless of what got reported.
- **Real bug caught by the new Filament panel tests**: `User::canAccessPanel(): bool { return $this->is_admin; }` throws a `TypeError` whenever `is_admin` reads as `null` in memory — which happens for any freshly-created model whose insert relied on the column's DB-level default rather than setting it explicitly (true of almost every seeded/factory user, since `UserFactory::definition()` never sets `is_admin`). Fixed with an explicit `(bool)` cast. This means every non-admin login attempt against the panel was one `TypeError` away from a 500 instead of a clean 403 — a real, previously-undetected bug, not a test-only artifact.
- **Filament panel tests need a dedicated `actingAsAdmin()` helper, distinct from the suite's global `actingAs()` override**: `Tests\TestCase::actingAs()` is globally routed through `Sanctum::actingAs()` (see the Phase 2 decision on this) because every API route uses the `sanctum` guard — but Filament's panel authenticates on the `web` session guard, so reusing that override left every panel-page test hitting a 302 redirect to `/admin/login` instead of the page. Added `actingAsAdmin()`, calling `parent::actingAs($user, 'web')` directly, alongside (not replacing) the existing override.
- **`phpunit.xml` needed a bumped `memory_limit`**: the full backend suite started hitting PHP's default 128M CLI limit once Filament's panel/resources are bootstrapped on every test alongside Intervention Image's GD driver decoding fake uploaded images (`ProductMediaTest`) — set to 512M via `<ini>` in `phpunit.xml`, scoped to test runs only.

Used the sign-in response's own transient `is_new_account` flag instead (`User::wasRecentlyCreated`, already surfaced from `firstOrCreate`/the OTP-verify creation branch) — true only for the literal sign-in call that just created the row, never again afterwards regardless of what `account_intent` holds. `account_intent` itself stays purely a data record of the choice (including `'later'`, which is a real recorded answer, not the same as `NULL`/unanswered).
  - **One shared `completeSignIn()` helper (`features/auth/presentation/post_sign_in.dart`) rather than duplicating the terms-then-intent sequence in each of the three sign-in call sites** (phone OTP, Google, Apple) — the ordering (mark authenticated → Terms/Privacy gate if unaccepted → intent screen only for a brand-new account → otherwise just close the sign-in UI) is exactly the kind of sequence that drifts out of sync between call sites if hand-copied, and Part 2's own spec is explicit that intent must never re-show for returning users, which is easy to get right once and easy to get wrong three times.
  - **`context.go`, not `context.push`, for every step of the new-account path** (`completeSignIn` → `/account-intent`, and each of that screen's three options onward). The intent screen is reached only once, right after the sign-in sheet is torn down — pushing it would leave the sign-in sheet's route (and, if pushed further, the intent screen's own route) sitting in the back stack for the user to accidentally navigate back into after they've already made their choice. `go()` replaces the whole stack at each step instead, so there's structurally nothing to go back to.
  - **`BeemSmsGateway` bound conditionally in `AppServiceProvider`, not swapped in as the new default.** The instruction was "falling back to the log driver when unset" — read literally as a closure over both config keys (`services.beem.api_key`/`secret_key`) rather than a fixed class binding, so local dev and CI (which never set Beem credentials) keep exercising the exact same `LogSmsGateway` path as before, with zero behavior change unless the two env vars are actually populated. Locked this in with `SmsGatewayBindingTest`, since a binding-selection bug here has a much worse failure mode than most (silently starting to send, or silently failing to send, real SMS in the wrong environment) than a typical wrong-branch bug.
  - **Beem's API contract implemented from documented behavior, not tested against a live account** (no credentials — this isn't one of the four credential blockers, since a real implementation exists either way, only real *keys* are missing). `BeemSmsGateway` posts `source_addr`/`encoding`/`message`/`recipients[].dest_addr` with HTTP Basic Auth, strips the leading `+` from the E.164 number (Beem expects a bare MSISDN), and treats anything other than `successful: true` in the response — including a non-2xx HTTP status — as a hard failure (`RuntimeException`, not swallowed), since a silently-dropped OTP send is worse than a loud 500 the client can retry. Documented the full account-setup/sender-ID-registration/funding chain a real deployment needs in `docs/SMS.md`, since none of that can be verified from this environment.
